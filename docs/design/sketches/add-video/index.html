    What “ready” means

    1. Transfer
      Copy the video to the server.
    2. Store and confirm
      A complete library item—not a temporary browser file.
    3. Attach subtitles
      Optional, and retryable without uploading the video again.
    4. Check playback
      Ready in this browser is not a guarantee for every device.

    Watching without learning-language subtitles is possible in the proposed flow. Word lookup and collection from subtitle text need those subtitles; they are not promised for a subtitle-free video.

    Proposal notes and limits

    One bounded direction, grounded in the owner’s desktop-browser addition requirement and the architect’s source assessment. File inputs are standard web controls, not desktop-only file-handle APIs.

    • Interrupted transfers restart from the beginning. Unknown results must be checked before another upload; a failed check is not proof that the video is absent.
    • Exact content match opens the existing item. A filename match alone must never replace an item. Existing subtitle tracks are not silently overwritten.
    • Selected subtitle roles are explicit. A failed subtitle attachment keeps the stored video and any successful subtitle; retry sends only the replacement subtitle.
    • Storage, admission, file validation, duplicate comparison and media compatibility are simulated. No automatic conversion is offered.
    • Cancel here models a server-confirmed cancellation of an incomplete upload. If confirmation is lost, production must use the uncertain-result path—not claim cancellation succeeded.

    Gate: verify. Friction: one deliberate add operation; retries do not repeat successful work. Evidence: owner goal and source assessment, not upload qualification. Scope: synthetic design artifact only. Earlier sketches untouched.
