## 1. Decision and bounded threat model

### What is protected

**PROPOSAL.** Prevent an unpaired caller from reading learner snapshots, transcript/job results or snippet bytes, overwriting state, scheduling or cancelling jobs, executing local commands, or deleting artifacts. Preserve the personal-local boundaries in [DECISIONS.md](../../DECISIONS.md) and the [safety review](../review/safety-privacy-boundary-review.md), especially its media-path contract at line 158.

| Actor / boundary | In scope and response |
| --- | --- |
| Unrelated webpage, including a different local development origin | Validate Origin before dispatch, not just in response headers. Block simple requests as well as preflighted requests. Require capability even when Origin is allowed. |
| Opaque-origin document (`Origin: null`), file page, sandboxed page | Reject `null`; no file-page exception. An absent Origin is a different case and still needs capability for protected operations. |
| Attacker-controlled hostname resolving to loopback / wrong service authority | Exact Host check, independent of socket binding and Origin; never authorize by DNS resolution or hostname suffix. |
| Non-browser caller / local automation without pairing | Loopback and a spoofed permitted Origin are insufficient. Require capability. |
| Paired browser or explicitly paired script | Same personal-operator authority; no per-user or per-route roles. Normal payload validation and provider consent still apply. |
| Other network machines | Explicitly configured trusted private LAN and same-origin Docker proxy are supported. Unpaired machines still get no private bytes/effects. No public, hosted or multi-user claim. HTTP does not encrypt capability or learner data: passive sniffing, active MITM, malicious LAN peers, compromised proxy/UI and Docker-admin access are outside assurance; use only an operator-trusted network. |
| Compromised UI origin, extension with UI access, same-user malware, administrator, stolen capability | Outside the assurance boundary. They may read memory, replace local software or act as the operator. Do not claim this bearer capability isolates OS users or defeats XSS. |

No browser exploit has been demonstrated. The source defect is the absence of a request-authenticity gate, not evidence that every browser can exploit it. Browser CORS enforcement, local-network permission prompts, DNS behavior and fetch metadata are not the server's authorization mechanism. `Referer` and `Sec-Fetch-*` must not substitute for the checks below; do not require them for native clients.

The authorized operator still explicitly supplies owned/local media paths. This decision adds **no media-library root allowlist**, no new permission to execute downloads, no provider enablement, no credential discovery, and no authentication framework, accounts, cookies, OAuth, TLS deployment or cloud sync. **Amended 2026-10-31 (`lt-192.9`):** one exception, the pairing-minted read-only media content cookie in §3 "Media content cookie"; no other cookie. It does not repair independent path portability, restore/revision, command configuration or job cancellation semantics.

### Choices and tradeoffs

1. **Use a process capability, not Origin-only trust.** Native clients can supply Origin/Host freely. A public HTTP token-discovery endpoint would erase the pairing boundary for them, so none is permitted. The cost is explicit pairing after service restart and browser reload.
2. **Protect reads as well as writes.** State and job results contain private material; snippet GET already mutates LRU metadata. Only minimal health stays unauthenticated. This changes current status/polling clients, deliberately.
3. **Exact public authority and UI-origin allowlists; bind is not identity.** Native default UI origin is `http://127.0.0.1:5173`. Preview `http://127.0.0.1:4173` is explicit startup opt-in, not an implicit wildcard. `localhost`/IPv6 are not aliases of the default origin. Changing these defaults later affects pairing and tests, not the basic protocol.
4. **Keep browser fetch-to-Blob snippet playback.** It can carry a capability header; direct `<audio src="http://.../api/snippets/...">` must not become a tokenless exception. No capability in media URLs.

## 3. Normative request policy

Everything in this section is **PROPOSAL**. All checks apply independently; a good capability does not override bad Origin/Host, and good Origin does not override a missing capability.

### Authority and Origin

- Validate startup configuration and private capability-delivery readiness **before state/scratch/model filesystem effects or API listener start**. For fixed-port native and Docker modes, freeze the complete exact request policy before listening; Docker retains all pre-listener requirements. The sole exception is native direct `port: 0`: validate the canonical configured hostname, bind, UI origins, envelope policy and private delivery first, then bind with **application admission DISABLED**. Obtain the OS-assigned actual port and freeze the complete immutable exact authority before initializing state/scratch/model resources; enable admission only after all initialization and delivery readiness succeed. Before readiness, reject/close every request at the transport boundary (including health, OPTIONS and `Expect: 100-continue`), with no body buffering, handler dispatch, private disclosure or request-attributable application effects; do not queue/replay it when ready. Failure keeps admission disabled and closes the listener. Preflight/bind/authority-freeze failures have no state/scratch/model effects. Initialization failures may require rollback/disposal of startup-owned resources already initialized: report those lifecycle effects separately, never claim initialization was effect-free, never delete pre-existing learner/model/scratch data as rollback, and never attribute cleanup to a rejected request. Native default bind remains `127.0.0.1`; Docker container bind `0.0.0.0` and explicitly selected trusted-LAN binds are permitted. Bind address is NOT an accepted HTTP authority. Native direct mode uses an explicitly selected canonical service hostname and actual listening port (including `port: 0` tests); bracket IPv6 correctly. Docker requires a nonempty explicit list of public HTTP origins, including browser-visible external port; never derive identity from `0.0.0.0`, container IP, request Host/Origin, or Vite implicit host rules.
- Require exactly one well-formed Host matching the immutable public-authority set for this mode. Native direct mode has one authority; Docker allows only enumerated public authorities. Exact DNS names, canonical IPv4 or bracketed IPv6 are allowed; wildcard/suffix matching, trailing dots, userinfo, shorthand/numeric alternate IP spelling and extra authority components are forbidden. Hostname comparison is case-insensitive; explicit ports are canonical decimal 1–65535. Omitted port matches only an explicitly configured HTTP default-port-80 authority; it never matches a nondefault port. No DNS lookup establishes trust.
- Docker proxy mode MUST preserve the original public Host unchanged; target `http://api:5174` selects only the upstream socket, never authority (`changeOrigin` must not rewrite Host). Both proxy ingress and backend validate that same explicit public-authority set; backend validates Origin unchanged. Proxy strips inbound `Forwarded` and all `X-Forwarded-*`; backend ignores them and never uses them to repair Host. Internal `api:5174` is not a public authority and cannot admit protected routes. A separate exact `127.0.0.1:5174` authority is allowed ONLY for local minimal GET health (Compose probe), never state/status/jobs/snippets/OPTIONS; reject it elsewhere with 403. Backend port remains unpublished. This eliminates trusted-forwarded-header enrollment and needs no proxy secret. Reject duplicate Host/Origin/Authorization/Content-Type fields (and, under the `lt-192.9` amendment, Cookie/Range/If-Range/Sec-Fetch-Site) via raw header inspection, not just Node's possibly joined/discarded representation. Transport-parser rejection is also acceptable for malformed framing.
- If Origin is present, require exactly one serialized origin equal to a startup-configured allowed UI origin. Default only `http://127.0.0.1:5173`. Optional exact local origins (e.g. preview `http://127.0.0.1:4173`) must be explicitly configured before startup. Only canonical HTTP origins with explicitly selected exact DNS/IP host and valid port may be configured; native dev/preview loopback and private-LAN origins are supported. Default-port 80 uses serialized origin without `:80`; reject other normalization aliases at configuration parsing. In Docker, allowed UI origins equal the configured public-origin set. Native direct mode has an independently explicit UI-origin set. No `*`, suffix match, credentials, path, query, fragment, `null`, `file:`, HTTPS assumption or request-driven enrollment.
- Missing Origin is allowed for a capability-bearing request; this is **not** a claim the caller is non-browser. Native tools need not forge Origin. Present-but-disallowed Origin fails even with a valid capability. Minimal health permits absent Origin but still rejects a present invalid one.

### Capability and pairing

- Generate a fresh unpredictable **32-byte** capability with OS-backed cryptographic randomness per service start; encode base64url without padding. Do not derive it from a port, origin, UUID job ID, time, machine identity or provider credential.
- Require one `Authorization: Bearer <capability>` on R02–R10. Validate the exact token encoding/length and compare equal-length bytes in constant time. Malformed/missing/wrong/stale capability returns 401 with a generic error and `WWW-Authenticate: Bearer realm="lingotorte-local"`; never echo it. No query/body/cookie/URL capability fallback. Health and valid OPTIONS do not require it. (The `lt-192.9` media cookie below is not a capability fallback: it is accepted only on `GET`/`HEAD /api/media/:id/content`.)
- **Minimal bootstrap selected:** explicit private operator-to-Settings pairing. Native mode uses a dedicated direct interactive TTY (not inherited logger stdout); Docker detached mode uses the local IPC receiver described below and a separate interactive `docker compose exec -it api` pairing helper. The helper displays the current process value only on its verified private controlling terminal, never stdout/stderr streams captured by Compose logs. UI has a masked session-capability input beside its exact service origin; the user pastes it and explicitly connects. Do not print it when stdio is redirected/inherited by a noninteractive logger. Never put it into startup JSON, Vite assets, HTTP health/status, an unauthenticated bootstrap endpoint, URL fragment/query, shell command arguments/history, or committed fixtures.
- For in-process synthetic tests/explicit local automation, add a local-only programmatic startup delivery seam (e.g. a callback receiving the generated capability); it is **new implementation work**, not an existing runtime option. It must not expose the value over HTTP or general config/status serialization. If neither a verified private interactive delivery path nor a reviewed local receiver is ready, fail startup before opening state or creating/cleaning scratch/model roots. No insecure unpaired fallback. Detached synthetic/private Compose operation is supported by the receiver below; persistent real-state rollout remains separately gated.
- Browser keeps capability in a nonserialized, in-memory paired-client object bound to one exact service origin, not SQLite, learner snapshot/export, localStorage, sessionStorage or ordinary logs. Clear the input after pairing. **Amended 2026-10-13 (`lt-z41` option C, under DECISIONS.md §14):** after an explicit opt-in "Remember this pairing on this device until the service restarts" and a successful authenticated status check, the browser may store `{origin, capability}` in a dedicated IndexedDB record that is separate from the learner snapshot cache. It is never included in snapshots/exports/logs. At boot a remembered pairing auto-connects. A 401, Forget pairing, unticking the opt-in, or an origin change deletes the record. Without the opt-in, reload still requires pairing again. Service restart invalidates all previous clients, remembered or not. Multiple explicitly paired tabs share operator authority, **not** write-conflict protection.
- URL edit/disconnect clears the active pairing and stops new authenticated work. In-flight requests retain their captured original origin/session and may not retarget a replacement endpoint; stale responses must not update the replacement connection. A 401 stops autosave/new jobs/poll loops with a generic “pair again” state; do not retry without credentials or replay a mutation automatically after pairing.
- Non-browser scripts use the same capability and exact authority; Origin may be absent. HTTP libraries can fake headers, so header assertions alone never enroll a script. Use private process memory/input for delivery, not provider keys or a general-purpose long-lived password. Same-user software that steals this value is outside the threat model.

#### Detached-container local secret-delivery boundary (new, review required)

The smallest proposed replacement is a process-owned Unix-domain socket in a dedicated container tmpfs `/run/lingotorte-pairing`, not a secret file/volume/config variable. Directory mode 0700 and socket mode 0600 belong to the non-root API uid; no host/shared-web mount, published socket port, Docker socket mount, or web HTTP route. Capability stays in API memory. Runtime startup must validate actual tmpfs mount, uid/modes, no symlink/foreign/stale endpoint, bind socket and verify a bounded local receiver round trip before any state/scratch/model effects or API listening; only this dedicated ephemeral IPC directory/socket setup is allowed beforehand. Do not silently chmod arbitrary existing paths, unlink foreign sockets, or fall back to disk. The IPC reply is bounded and contains only process capability; no state/provider credentials. Receiver readiness is delivery availability, not proof the human has paired.

A separate helper executed by an already-authorized Docker operator as the API uid requires a genuine controlling TTY and writes directly there; it never accepts an output-file option or emits secrets to piped stdio. Docker exec authority and same-uid container filesystem permissions are the local authorization boundary (not HTTP or a claim of Unix peer-credential verification by Node). Other same-uid software/root/Docker administrators are trusted; other containers/network peers are not. Bounded connections/timeouts, no secret diagnostics, and shutdown socket disposal are required. Repeated explicit local retrieval during one process lifetime is permitted to pair reloads/tabs; no secret rotation by HTTP. Restart destroys socket/process memory and rotates capability. Failure/loss of receiver during runtime suspends new protected admission until restored or fails service closed; no tokenless mode.

Prove detached `up -d`, local interactive retrieval, wrong uid/permission, non-TTY refusal, invalid tmpfs, startup receiver failure, restart invalidation and logs/config/export absence using disposable synthetic containers before accepting this mechanism. If reliable private TTY display or mount verification cannot be achieved, block detached startup rather than print a token or store one persistently. No real deployment, hosted authentication, accounts or TLS deployment is added.

#### Media content cookie (amendment `lt-192.9`, 2026-10-31)

Janusz selected the option "Approve the reviewed HTTP/HTTPS media-cookie design and its stated limits" ([DECISIONS.md §14b](../../DECISIONS.md); design [`server-media-private-access-design.md`](../design/server-media-private-access-design.md) §3). This amendment text is a candidate pending independent review with D (`lt-192.4`). It is not implementation or runtime acceptance. A `<video>` element cannot send the bearer, so exactly one cookie is allowed:

- **Value.** The `lt_media` value is 32 bytes of OS randomness, base64url-encoded, generated independently of the capability. It is kept only in service memory, in a bounded set that evicts the oldest value. It is never written to disk, logs, status or exports, and never put in a URL.
- **Mint (M1).** `POST /api/media/session` requires the bearer, full admission and a JSON body of exactly `{}`. It returns `204` with `Set-Cookie: lt_media=<value>; Path=/api/media/; HttpOnly; SameSite=Strict`. `; Secure` is added only when the configured public origin is `https:`. There is no `Domain` and no `Max-Age`. M1 rotates: a presented `lt_media` value is removed before the new one is minted (D correction R2), so a confirmed M2 of the latest value also ends every earlier value this browser held. A denied M1 has zero effects.
- **Revoke (M2).** `DELETE /api/media/session` requires the bearer and takes no body. It removes the presented value when there is one, and always returns `204` with the same attributes plus `Max-Age=0`. Without a valid bearer it returns 401 with zero effects, and the value stays valid.
- **Accept (M4).** The cookie is accepted only on `GET`/`HEAD /api/media/:id/content`, as an alternative to the bearer. The Host, Origin and target checks above run first and are unchanged. Three rules follow. The first two apply whatever credential is sent; a valid bearer never exempts a request from them.
  - **Duplicate fields.** `Cookie`, `Range`, `If-Range` and `Sec-Fetch-Site` join the raw duplicate-field rule (§3 "Authority and Origin"). A second field of any of them returns 400 at the malformed-header stage, on every route.
  - **Fetch Metadata, M4 `GET`/`HEAD` only.** After route and method resolution and **before either credential is examined**, a present `Sec-Fetch-Site` other than `same-origin` returns 403. An absent header is allowed. The check never applies to other routes or to OPTIONS.
  - **Credential precedence, between the two credentials only.** If an `Authorization` field is present, the bearer rules alone decide. A missing-scheme, malformed, wrong or stale bearer returns 401 and never falls back to the cookie, even when a valid `lt_media` value is also sent. Only when `Authorization` is absent does the cookie decide: exactly one `lt_media` pair, compared in constant time, is accepted; no pair, two pairs, or an unknown or malformed value returns 401. Both paths also require private delivery to be ready.

  The cookie is ignored on every other route.
- **Effects and response.** M4 has no application side effects (§4). Its responses add `X-Content-Type-Options: nosniff` and `Cross-Origin-Resource-Policy: same-origin`. `Access-Control-Allow-Credentials` is never sent.
- **HEAD and Range.** `HEAD` ignores `Range` and `If-Range`. A successful `HEAD` is always `200` with the full-representation headers (`Content-Length` of the whole blob, `Accept-Ranges`, `ETag`, `Content-Type`), never `206` or `416`, even for an unsatisfiable or reversed range. It opens no read stream. Every `HEAD` response, success or error, has no body. On `GET`, a reversed `a-b` with `b < a` is invalid and gets `200`.
- **Browser.** Only M1 and M2 use `credentials: 'same-origin'`. Both are bearer-authenticated and are made only in the same-origin profile. Every other request keeps `'omit'`. Native direct mode keeps browser-local playback. M1 and M2 are serialised per page (D correction R2): while M2 runs no M1 starts, and M2 is sent only after every outstanding M1 settled (bounded); Disconnect then allows no further M1 for that pairing, Forget only an explicit playback re-mint. "Revoked" is reported only for an M2 `204` with no unsettled or uncertain M1 (timeout or network error). An M2 `401`, or a pairing already lost after a mint, is disclosed as an unconfirmed revocation: a `401` can come from unready private delivery without any value rotating (D correction R3).
- **Lifetime.** A service restart invalidates every value. Eviction and M2 end a value earlier. A browser may keep a stale copy, which is useless after a restart.
- **Accepted limits.**
  - Over LAN HTTP, a same-site page on another port can make the browser send a cookie-bearing request that the server cannot tell apart from the app's own. The server may read and send the bytes; CORP only stops delivery to that page. The guarantee is no mutation, not no read.
  - Cookies are not isolated by port (RFC 6265 §8.5).
  - When the service is unreachable or M2 fails, Forget or Disconnect cannot revoke the HttpOnly value, and the UI must say that access ends at the next service restart.
- **Acceptance.** Design §7 rows N01–N13 and N22–N27, plus the credential × Fetch Metadata × duplicate-field cross-product in the [D plan](../plan/lt-192.4-server-playback-plan.md) §5, under the §4 invariant and the §5 observation method. Real-browser rows stay real-browser rows.

### Route, method, body and dispatch order

Use a single route table/gate before handler effects, including binary/204 responses. Do not scatter partial checks through `sendJson`.

1. Validate Host, Origin and request-target syntax. Accept origin-form canonical API paths only; no absolute-form target, query/fragment, backslash, dot-segment normalization, percent-encoded routing escape or proxy target. No API currently needs a query string. Keep identifier matching consistent with emitted IDs and the existing snippet UUID route.
2. Resolve known route and allowed methods. Unknown route: 404. Known route, wrong method: 405 with `Allow` listing that route's methods plus OPTIONS. No HEAD/TRACE/PATCH/CONNECT fallback or method override from headers/body/query; HEAD is admitted only where a route lists it (M4, §3 "Media content cookie"). This classification performs no state/job/snippet lookup.
3. For OPTIONS, apply the preflight policy below and return without dispatch. On M4 `GET`/`HEAD` only, apply the Fetch Metadata check and then the bearer-or-cookie rule (§3 "Media content cookie"). Every other route requires the capability, except health.
4. Validate envelope and read only bounded permitted bodies. Preserve the existing 5 MiB ceiling for JSON bytes, measured while streaming (not trusted Content-Length). Reject unsupported Content-Encoding; do not decompress bodies. Do not read unauthorized bodies into application buffers. Reject/close or boundedly discard at the transport level without invoking any handler; avoid unbounded draining. Handle `Expect: 100-continue` through the same admission gate rather than treating it as permission to dispatch.
5. For PUT state and POST jobs/cancel/cleanup, require `application/json`, optionally one `charset=utf-8` parameter; compare media type/charset case-insensitively with legal whitespace. Reject all other parameters/charsets, absent type, `text/plain`, form-urlencoded, multipart, vendor JSON and other types with 415. Parse valid JSON object before effects; no empty-body-to-`{}` conversion. Cancel/cleanup require exactly `{}`. Malformed/empty/nonobject/unexpected cancel/cleanup fields: 400. Oversize: 413.
6. GET/DELETE/OPTIONS accept no request body and no Content-Type. Reject declared nonzero length, transfer-encoded body or unexpected body bytes before side effects; zero Content-Length is fine. Unsupported Content-Type on these routes: 415; body/framing violations: 400. Node-level malformed framing may close the connection instead. Set finite transport body/header timeouts; this is not a general denial-of-service guarantee.
7. Only after successful gate and envelope validation may the matched handler read private state, alter maps/counters/lifecycle, save SQLite, start a job/command/provider operation, or clean/delete artifacts. Existing semantic payload validation remains necessary; capability is not provider consent or media-rights proof.

For multi-fault requests, follow this order: malformed authority/headers/target 400 (including a duplicate `Cookie`, `Range`, `If-Range` or `Sec-Fetch-Site` field, whatever the credential); well-formed wrong Host or Origin 403; route/method 404/405; on M4 `GET`/`HEAD` only, a present `Sec-Fetch-Site` other than `same-origin` 403; capability or media cookie 401; encoding/media type 415; body size/JSON/shape 413/400. Tests should normally change one condition at a time. Errors must not contain request secrets, private paths, payloads, notes or cue text.

### Preflight and CORS are response mechanics, not authorization

- OPTIONS needs valid Host, known path, one allowed Origin, exactly one `Access-Control-Request-Method` permitted for that route, and a case-insensitive requested-header set contained in `{authorization, content-type}`. Duplicate/malformed preflight control fields: 400. Missing Origin/requested method: 400. Forbidden Origin/requested method/header: 403. No body; no actual bearer value is required or issued.
- A protected route's requested-header set must include `authorization`; POST/PUT must also include `content-type`. Missing those expected names: 403. Health GET permits an absent/empty requested-header set. Private-network preflight is disabled by default. An explicit immutable per-UI-origin native-direct opt-in may admit exactly one `Access-Control-Request-Private-Network: true` only after all other preflight checks, returning `Access-Control-Allow-Private-Network: true`. False/other/duplicate values are 400; true without this opt-in is 403. Docker same-origin mode has no such opt-in and returns 403 for true. This is a narrow browser access permission, not pairing/authorization; record actual browser local-network prompts/blocks and preserve independent actual-request checks.
- Successful preflight: empty 204, no JSON body, allowed exact Origin, requested permitted method, allowed requested headers, `Vary: Origin, Access-Control-Request-Method, Access-Control-Request-Headers` (also `Access-Control-Request-Private-Network` when evaluating that field), `Cache-Control: no-store`; omit preflight max-age initially. It never creates a session or reserves a job. Unknown OPTIONS path: 404.
- For actual requests with validated Host and allowed Origin, add that exact `Access-Control-Allow-Origin` and `Vary: Origin`, including allowed-origin error responses (so the UI can see a 401/415). No wildcard, no `Access-Control-Allow-Credentials`, no Set-Cookie (sole exception: the `lt-192.9` media cookie on M1/M2 responses, §3 "Media content cookie"). Missing Origin gets no CORS grant. Wrong Host/disallowed Origin gets no CORS grant. Apply consistently to JSON, WAV and 204 deletion responses.
- Each actual request is independently gated even if a browser cached a successful preflight. Native callers do not need to send OPTIONS. A denied preflight must have no more application side effects than any other rejected request.

### Browser transport destination safety

Before attaching capability **or sending learner state**, parse/validate destination locally. Docker `/` means a captured canonical `window.location.origin`, not a relative mutable base or the browser machine's localhost backend; pairing displays and explicitly confirms that exact HTTP origin. Native direct mode permits an explicitly entered canonical HTTP loopback or operator-selected private-LAN origin, optional root `/`, no username/password/path prefix/query/fragment. No DNS-based privacy inference: selecting a LAN name/IP is an explicit trust assertion, not proof it is private. Public-internet/arbitrary remote deployment is unsupported. A different private-LAN destination requires a separate explicit operator trust selection and fresh pairing; old capability/snapshot must never follow it. Endpoint selection must be a user action, not server response, discovered Host/Origin or redirect. Reject deceptive IP spellings, wildcard origins, `file:`, `data:`, `blob:`, `javascript:` and unsupported HTTPS; no TLS deployment is introduced. HTTP cannot prove endpoint authenticity or protect data/capability from sniffing/MITM; the UI must warn before LAN pairing.

Use a shared paired transport for model and snippet requests, with `credentials: 'omit'` (sole exception: media-cookie mint and revoke use `'same-origin'`, §3 "Media content cookie"), `redirect: 'error'` and no `no-cors` fallback. Do not set Origin manually in browser JavaScript. Validate any server-supplied snippet path against `/api/snippets/:uuid` before constructing the URL; never follow an absolute/protocol-relative result URL or route to another authority. Keep capability out of Blob/audio URLs. A base-URL change cannot carry an existing capability or snapshot to the new destination automatically.

## 4. Reject-side-effect invariant

**PROPOSAL / TEST REQUIRED.** A request rejected by this admission policy (authority, Origin, method, capability, preflight, encoding, media type, body size/JSON/envelope) has **zero request-attributable application side effects**:

- no persistence save/transaction, audit/event append, durable revision change, or learner/provider-policy change;
- no job ID allocation/queue/map insertion, job status/cancel update or worker dispatch;
- no command runner, media read, provider HTTP call or new scratch/model artifact;
- no snippet registration, LRU touch/eviction, deletion, cleanup scheduling, lifecycle transition or drain of running work;
- no private response bytes, generated token, raw request logging, or secret-bearing error.

A small generic denial response is allowed. Application counters (including IDs/access/revisions/audit) must not change; optional isolated bounded transport-denial diagnostics are excluded only if explicitly classified, contain no private data, and cannot influence application behavior. Startup/normal shutdown cleanup is a separate operator lifecycle action; take negative-test baselines **after** startup and inspect **before** shutdown. An already-authorized background job may progress concurrently; use a gated fake runner and prove rejection neither cancels/drains it nor changes its result/publication behavior.

Do not hide a rejected request by returning an error after queuing work. Conversely, an authenticated request accepted as a job and later failing payload/provider validation is a job failure, not a request-policy rejection. Baseline provider-disabled jobs currently create a failed job record; this decision does not relabel that behavior as side-effect-free. Snapshot semantic/transaction validation and whole-job preflight remain their own correctness contracts. All admission checks and JSON/envelope failures specified here must occur before those business handlers.
