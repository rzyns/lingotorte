## Outcome and interface

- `privateDelivery.ts` implements process-memory-only delivery. Linux native mode opens `/dev/tty` directly, verifies genuine controlling devpts device from kernel `/proc/self/stat`, API uid and private read permissions, and rechecks availability. It does not use inherited stdout/stderr. Unsupported platforms/noninteractive invocations fail closed. **Windows native CLI private-console delivery is not implemented/qualified**; Windows programmatic startup callbacks remain available, and Docker-primary runtime was exercised on this Windows host.
- Docker mode binds `/run/lingotorte-pairing/receiver.sock` only after verifying an actual exact tmpfs mount, non-root API uid and non-symlink 0700 directory. Existing endpoints are rejected, never unlinked/adopted. The newly owned socket is 0600, with bounded 16 simultaneous connections, five-byte `PAIR\n` request, 44-byte reply, and one-second timeout. Process capability stays in service memory. Readiness performs an owner/mode/inode check and actual local roundtrip. Loss/permission change rejects new protected work. Disposal is limited to the owned socket identity.
- `scripts/pair-local.ts` requires a private controlling TTY and uses direct terminal writes; no output-file argument or stdout/stderr secret fallback. Docker operator recipe: `docker compose -p <explicit-project> exec -it --user 1000:1000 api node scripts/pair-local.ts`. Paste only into the masked pairing UI. No capability environment variable, HTTP endpoint, URL, config/export field, persisted secret file or shell argument was added.

Callback receives one fresh 32-byte OS-random base64url value; it is absent from the returned service/config and HTTP serialization. - CLI nonsecret options: `LINGOTORTE_PRIVATE_DELIVERY=tty|socket` (default tty); `LINGOTORTE_SERVICE_HOSTNAME`; comma-separated exact `LINGOTORTE_PUBLIC_ORIGINS`, `LINGOTORTE_UI_ORIGINS`, `LINGOTORTE_PRIVATE_NETWORK_ORIGINS`; `LINGOTORTE_HEALTH_AUTHORITY`; existing bind/port/path settings.
