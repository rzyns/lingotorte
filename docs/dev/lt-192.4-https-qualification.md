## Contract delta (minimal)

1. **Exact origins.** `canonicalOrigin` accepts exact serialized `http:` **and** `https:` origins. An https default-port origin is written without `:443`. Every alias spelling is still refused: uppercase scheme or host, `:443`, userinfo, path, query, fragment, trailing dot, wildcard, numeric/shorthand IPs, leading zeros, and other schemes.
2. **Host selects the origin.** `freezePolicy` builds `originByAuthority`, so each admitted Host authority names exactly one configured public origin.
   - HTTP keeps its existing behaviour: Host `x:80` folds to `x`.
   - An https default-port origin is reached by Host `x` (what browsers send) and by the native spelling `x:443`. No blanket Host normalisation was added.
3. **Ambiguity is refused at startup.** Host carries no scheme, so the scheme is never guessed. Startup refuses any public set where one authority could mean two origins: `http://x` + `https://x`, `http://x:443` + `https://x`, `http://x:8443` + `https://x:8443`, and `https://x:80` (unreachable, because Host `x:80` folds to `x`).
4. **Per-request `Secure`.** `admit()` returns the Host-selected `publicOrigin`. M1/M2 add `Secure` only when that origin is `https:`. Before this change, `Secure` came from the first configured public origin.
   - `Forwarded`, `X-Forwarded-*` and `Tailscale-*` never select scheme, host or identity. The ingress still strips `Forwarded`/`X-Forwarded-*`, and the backend ignores all three.
5. **Exact same-origin M1/M2.** A present `Origin` on M1/M2 must equal the Host-selected origin exactly (scheme, host and port). The old check compared it with `http://${host}`. This blocks a configured http origin from minting or expiring the cookie on an https Host, and the reverse, even though both origins are independently allowlisted.
6. **Profile limit.** `https:` is allowed only in the explicit public-origin (Docker/TLS-front-end) profile. Native direct mode with an `https:` UI origin fails startup. Private-network-access opt-in stays native/HTTP-only.
7. **Browser transport.** `exactServiceOrigin` accepts canonical `https:`, including the captured page origin `/`. The M1/M2 `credentials: 'same-origin'` exception still requires the transport origin to equal `location.origin` exactly, so a scheme mismatch is refused before any request leaves the browser.
8. **Settings copy.** For an `https://` service URL the warning reads "HTTPS encrypts only up to the operator's TLS front end". The "HTTP sends capability and learner data unencrypted" sentence stays for `http:`. The pairing-error text is unchanged.

Unchanged guards:

- the separate health authority (health-only);
- CORS exact-origin grants, with an unchanged independent allowlist for non-M1/M2 routes;
- the raw duplicate-field rule;
- method/route/body/encoding gates;
- M4-only Fetch Metadata;
- "a present Authorization decides alone", with no cookie fallback;
- cookie accepted only on M4;
- the zero-effect denials.

The service still terminates no TLS, and no production TLS server was added.

**Recorded limit (unchanged).** Media cookie values are not bound to the minting origin. With several configured origins, a value minted under one is accepted on M4 under another configured authority. Browsers withhold a `Secure` value from `http:`. Tested and documented as a limit, not changed.

## The HTTPS browser proof [TLS-browser]

The setup runs in one disposable container: network `none`, no mounts, no published ports.

- **TLS front end.** `tls-proxy.mjs` is a small stdlib `node:https` → `node:http` reverse proxy with HTTP/1.1 ALPN. It preserves Host and raw headers, streams bodies and aborts upstream on client close. It bound **port 443** inside the container, so the origin is `https://lt-https.test` with no port.
  - Like Tailscale Serve, it adds forwarding/identity headers: `x-forwarded-proto`, `x-forwarded-host`, `x-forwarded-for`, `forwarded`, `tailscale-user-login`, `tailscale-user-name`. Their values are deliberately **wrong** (http, a spoofed host, a fake identity).
  - Behind it run the unchanged Vite dev origin, the exact-Host public ingress and `/api` proxy, and the real service with a synthetic library and database in `/tmp`. Providers are forbidden.
  - Public origins: `https://lt-https.test` plus `http://lan.test:18462` (a mixed, unambiguous configuration).
- **Certificate.** `tls.sh` generated it on the host with the openssl CLI (OpenSSL 3.5.5), outside the repository: P-256, `CN`/SAN `DNS:lt-https.test`, valid 2 days. A second, unpinned pair served as the negative control. The files were copied in with `docker cp` and deleted from the host after the runs. No key entered the repository, an image, a log or the host trust store.
  - Public facts: cert DER SHA-256 `bd3f743c1c88c11e51869a793ca8b5b6c01bd0ef3b71d6eb562cf007a9d62085` (PEM-bytes SHA-256 `22bdd2a3…f9c55b`, as printed by the proof); SPKI pin `bSIel23HyHQOxE8dlDEKnIOp0Dq+rswELB1LofzQ6G0=`; unpinned cert DER `94c99d76…a548ff`.
- **Browser.** Chromium is launched with `--host-resolver-rules=MAP lt-https.test 127.0.0.1` and `--ignore-certificate-errors-spki-list=<pin>`. That flag ignores errors **only** for this key; `ignoreHTTPSErrors` is **not** used. Row T0 proves the scope: the same name with an unpinned certificate fails with `net::ERR_CERT_AUTHORITY_INVALID`.
