## 1. Scope

**In D [rec]:**

- **Routes.** M1 `POST /api/media/session` (mint), M2 `DELETE /api/media/session` (revoke), M3 `GET /api/media/:id/storage` (bearer) and M4 `GET`/`HEAD /api/media/:id/content` (bearer or `lt_media` cookie).
- **Storage.** One read-only managed-blob store under an optional `LINGOTORTE_LIBRARY_DIR`, plus migration **v14** for the ready table.
- **Client.** The derived playback source, the `checking-access` recovery path, and M2 on Disconnect/Forget.
- **Proof.** Synthetic Node and real-browser proofs.

**Not in D:**

- U1–U4 uploads, staging writes, ffprobe and A1 attachment (all E).
- Compose, Dockerfile, `/library` volume or https-origin enablement (configuration authority, design §9.2).
- Any change to pairing, the bearer or Host/Origin rules.
- Transcoding, and blob deletion or GC.

**No production writer of blob rows exists in D.** Until E ships, a real deployment always reports M3 `none` and behaves exactly as today. Section 6 explains how tests register synthetic blobs.

**D acceptance stays open after the code lands [rec].** `lt-192.4`'s acceptance criteria require play/seek "in desktop Chrome and actual iPad browser". The design's E1 and E6 (iPad) and B1–B5 (boundary) are owner- or device-gated and excluded here. A green synthetic suite, plus independent review, makes D an **implementation candidate only**. "No recurring pairing" is neither delivered nor promised: pairing stays required on every route except M4, and on M4 the cookie itself is minted by pairing.

## 4. Target design [rec]

### 4.1 Server: two new deep modules, wiring only in the hotspots

**`apps/local-service/src/mediaSessions.ts` (new).** Holds the in-memory cookie set:

```ts
export const MEDIA_SESSION_CAP = 64;
export type MediaSessions = Readonly<{
  mint(): string;                                   // 32 random bytes, base64url (43 chars); evicts oldest beyond cap
  revoke(cookieHeader: string | undefined): void;   // removes the single presented lt_media value, if any
  check(cookieHeader: string | undefined): 'absent' | 'valid' | 'invalid';
  size(): number;                                   // observeState seam only
}>;
export function createMediaSessions(cap?: number): MediaSessions;
export function mediaSessionCookie(value: string | null, secure: boolean): string; // null => expiring cookie
```

- Values are stored as an array of at most 64 `Buffer`s, compared with `timingSafeEqual` against every entry; there is no hash lookup. The format check mirrors the bearer check (`requestAdmission.ts:104-106`).
- Cookie parsing splits on `;` and counts `lt_media` pairs: zero means `absent`; more than one, or a malformed or unknown value, means `invalid`. Other cookies are ignored.
- There is no TTL and no touch-on-use (§4.3).

**`apps/local-service/src/managedMedia.ts` (new).** Owns the library, M3 and M4:

```ts
export const MAX_MEDIA_SLOTS = 16;                                          // global: pending opens + live streams, M3 and M4
export type MediaStorageState =
  | { state: 'none' } | { state: 'bytes-missing' }
  | { state: 'complete'; sizeBytes: number; mimeType: ManagedMimeType };
export type ManagedMedia = Readonly<{
  storage(res: ServerResponse, mediaId: string): Promise<MediaStorageState | 'busy' | undefined>; // undefined = unknown id; 'busy' => 503
  serveContent(req: IncomingMessage, res: ServerResponse, mediaId: string): Promise<void>; // every GET/HEAD status
  activeSlots(): number;                                                     // observeState seam only
  pendingOpens(): number;                                                    // observeState seam only
  shutdown(): Promise<void>;                                                 // close(): refuse, destroy streams, await pending opens
}>;
export async function openManagedMedia(root: string, blobFor: BlobLookup,
  options?: { maxSlots?: number; fs?: BlobFs }): Promise<ManagedMedia>;      // fs: test-only barrier seam for open/fstat/close
export function selectRange(range: string | undefined, ifRange: string | undefined, etag: string, size: number): ByteRange; // pure, GET only
```

- **Startup** (throws a `TypeError` so startup fails closed):
  - `fs.constants.O_NOFOLLOW`, `fs.constants.O_NONBLOCK` and `process.getuid` must exist. A Windows host with the library configured fails startup, rather than silently dropping the protection.
  - `assertLibraryPath` (G3) runs first: lexical **and** resolved overlap, both directions, against state, database, scratch, models, home, repositories and `/media`.
  - The root must `lstat` as a non-symlink directory owned by the uid, with `realpath === root`, and `access(W_OK)` must succeed (G3; a permissions check, not confinement).
  - Only after every check above passes is `blobs/` created with mode 0700 when absent; the same checks then run on it.
  - All of this runs **before** any other filesystem mutation, the database open and any state or scratch effect (`server.ts:786-797`).
- **Blob open:** the path is built only from the validated 64-hex digest. The file is opened with `O_RDONLY|O_NOFOLLOW|O_NONBLOCK` (G15; `ELOOP` → missing), `fstat`ed (it must be a regular file of exactly `size_bytes`; a FIFO, directory, device or socket is closed and treated as missing), and streamed from that handle only (design §5.2).
- **Open lifecycle (M3, M4 `GET` and `HEAD`) (G16):**
  1. **Reserve synchronously.** Before the handler's first `await`: if `closing` is set or the slots are at `MAX_MEDIA_SLOTS`, answer 503 with `Retry-After: 1` (no body for HEAD). Otherwise take a slot, create a pending record and register it in the pending set, and attach one `close` listener on the response that marks the record aborted. Single-threaded JavaScript makes this check-and-take atomic only because no `await` separates them.
  2. **Open, then recheck.** After `open` resolves, if `closing` or `aborted` is set, close the descriptor and release; never stream. A request abort or shutdown does not cancel the in-flight `open` (G16); the open is allowed to finish, which `O_NONBLOCK` keeps prompt for a FIFO, and its descriptor is then closed. An open error (`ENOENT`, `ELOOP`, others) releases the slot and answers 404 (M3: `bytes-missing`).
  3. **`fstat`, then recheck.** The same `closing`/`aborted` recheck follows. A non-regular file or a size mismatch closes the descriptor, releases, and answers 404 (M3: `bytes-missing`).
  4. **Finish.** M3 and HEAD close the descriptor and release before writing the response. GET hands the handle to `createReadStream({start, end})` with backpressure through `pipe`; from then on the stream owns the descriptor, and release happens on stream or response `close`.
  5. **Exactly once.** One guarded `release()` per record decrements the slot, removes the pending record, and closes the descriptor unless the stream owns it. The descriptor is closed by `release()` or by the stream, never both. A close failure is not retried (Linux `close(2)`: "Retrying the close() after a failure return is the wrong thing to do", because the kernel has already freed the descriptor, https://man7.org/linux/man-pages/man2/close.2.html). It does not change a response already decided, logs nothing with a path, and still frees the slot.
  6. **Shutdown.** `shutdown()` sets `closing` so new requests get 503, destroys live streams and their responses, then awaits every pending record until each has settled and released. The pending set stays non-empty until then, so `close()` cannot resolve while an open is unaccounted for.
- **M3:** media id → `managedBlobForMedia` → the open lifecycle → `complete`, `bytes-missing` or `none`. The client treats an M3 503 like any other non-OK M3 result: no `src` is set.
- **M4:**
  - GET headers: `selectRange` → 200, 206 or 416; `Accept-Ranges: bytes`; `ETag: "sha256-<hex>"`; `Content-Type` from the row allowlist; `X-Content-Type-Options: nosniff`; `Cross-Origin-Resource-Policy: same-origin`; `no-store` comes from admission.
  - **HEAD ignores `Range` and `If-Range` and never calls `selectRange` (G14).** A successful HEAD is `200` with the GET full-representation headers (`Content-Length` = blob size, `Accept-Ranges`, `ETag`, `Content-Type`, `nosniff`, CORP), never `Content-Range`, 206 or 416, even for an unsatisfiable or reversed range. It `fstat`s, closes, and never creates a stream or writes a body.
  - Every HEAD error (400/401/403/404/503, and 405 on routes without HEAD) has no body: `deny()` and the M4 error writer send headers only when the method is HEAD. Tests read the raw socket rather than rely on Node dropping it (design §5.3).
  - There are no effects: no LRU touch, no logging, no database write.
- **`selectRange` (GET only):**
  - The unit is case-insensitive ([doc] RFC 9110 §14.1, "All range unit names are case-insensitive"). Only one spec of the form `a-b`, `a-` or `-n` is accepted; anything else is ignored and gets a 200. A reversed `a-b` with `b < a` is invalid (RFC 9110 §14.1.1) and gets a 200.
  - Digits are compared as `BigInt` after a `^\d+$` test. `a ≥ size` and `-0` give 416 (RFC 9110 §14.1.2: satisfiable only if first-pos < length or the suffix-length is non-zero). `b` and an oversized suffix clamp to the file size.
  - An `If-Range` that differs from the ETag gives 200. Clamped values are below `size`, which is below 2^53, so they are safe as `Number` for `createReadStream`.

  - `recoverServerPlayback(model, video, code)` runs design §5.6 steps 1–5, with at most one re-mint per media, source and error sequence. Before `video.load()` it clears `model.player.mediaError`, so the repeat check at `stage.ts:287` cannot swallow the next error.
  - The same-origin profile means `transport.origin === location.origin`.
- **`model.ts`:**
  - `mediaPlaybackUrl` and `needsMediaRelink` delegate to `playbackSource`, keeping their signatures so callers do not change.
  - After a status OK in `connectLocalService`, if the profile is same-origin and `managedMedia.available`, call M1 and then M3 for the current media, without blocking.
  - On current-media change, call M3 and rerender with the result.
- **`stage.ts`:**
  - The gate and key use the derived source, and message states are rendered.
  - On `error` from a server source, call `recoverServerPlayback` instead of recording relink advice.
  - Managed media gets its own decode text (design §5.4); the relink advice at `:364` stays for local files.
  - Keep **no** `crossorigin` attribute: a CORS-mode media request would need `Access-Control-Allow-Credentials`, which the contract forbids.
- **`settings.ts`:** on Forget and on Disconnect, call `revokeMediaSession` first, then do the existing work (G2). On `not-revoked`, show the design §3 sentence.

### 4.3 Design it twice: the three non-trivial choices

1. **Where the cookie is checked.**
   - A, inside `admit`, is the one gate the contract requires ("a single route table/gate before handler effects", contract §3).
   - B, a bypass in dispatch, would duplicate Host/Origin checks and create a second gate.
   - **A** wins. Confidence high.
2. **How tests get blobs.**
   - A: a test helper writes `blobs/<hex>` (mode 0400) and inserts the row through a raw `DatabaseSync` on the synthetic database. Existing suites already do raw-SQL setup (`tests/core/durableReplace.test.ts:56`).
   - B: a production `registerManagedBlob`.
   - **A** wins. B adds a write surface that D has no caller for, and E must compose it inside its own deciding transaction anyway (design §6). It would change only if E needs a different row shape, which would mean a v15 `ALTER`; the table follows design §5.1 to avoid that.
3. **Bounding the cookie set.**
   - A: oldest-by-mint eviction, cap 64.
   - B: the same, plus rotating out the presented value on M1.
   - **A** wins because it is the approved text. B is safe and would reduce eviction pressure, but it is a behavioural extension that needs review.

**Routine constants, resolved with evidence [rec]:**

| Constant | Value | Evidence |
| --- | --- | --- |
| Cookie cap | 64 | A browser profile holds one `lt_media` per host and path, and re-mint replaces it in the jar. Only stale server copies accumulate, one per connect. 64 means 64 mints elsewhere since the victim's own mint, and recovery heals an eviction with one re-mint (N26). Memory is 2 KiB. Touch-on-use is ruled out because M4 must have no effects (design §3). |
| Cookie TTL | none (process lifetime, revoke or eviction) | The bearer has no TTL either (contract §3). A shorter TTL would 401 mid-film, then re-mint and reload: a user-visible stall for no gain within the §14 threat model. |
| Concurrent streams | 16, then 503 + `Retry-After: 1` | Chromium allows 6 connections per host group ([doc] https://chromium.googlesource.com/chromium/src/+/9e494a61899ecf7656fcd975931c129ac86e9fc4/net/socket/client_socket_pool_manager.cc). 16 covers two devices (the iPad Safari limit is **[unverified]**) and bounds file descriptors. The browser proof records the observed peak. |
| Timeouts | unchanged (`server.ts:766-769`) | See G11. |

## 7. Proxy and browser flows (run only when the parent schedules them)

**Proxy (Node).** Through Vite preview with `publicIngress` and the proxy:

- 200, 206 and 416 have byte parity with the direct responses.
- `Set-Cookie` arrives unchanged; there is no rewrite (`node.js:17158-17166`). The `Cookie` header is forwarded.
- HEAD returns zero body bytes.
- A client abort mid-stream drops `activeMediaSlots` back to 0 (`node.js:17306-17308`).
- `X-Forwarded-*` and `Forwarded` are stripped; a wrong Host gets 403 at ingress.

**Browser proof.** `scripts/qualification/lt-192-4/browser-proof.mjs` (new) follows the `lt-192-3` pattern: one disposable container, `--network none`, the real service and a Vite origin, synthetic data only, providers off, and the capability typed into the masked field and never printed.

- **P1 Pair.** M1 returns 204. CDP `Network.getCookies` is checked for attributes only (`httpOnly`, `sameSite: Strict`, `path: /api/media/`, `secure: false`, session cookie); the value is never printed. `document.cookie` lacks `lt_media`.
- **P2 Play.** WebM plays from the server with no relink placeholder: `readyState ≥ 3` and `currentTime` advances.
- **P3 Seek.** Seek to 75%: a Range request appears in the server counters and the bytes served stay below the file size.
- **P4 Pause.** Pause for more than 15 s, then resume (E4).
- **P5 Restart.** Restart the service: `checking-access`, then M3 401, then *pair again*, with no decode advice. After re-pairing, playback works (E5).
- **P6 Eviction.** 64 bearer-minted values from a Node client evict the browser's value. The next request recovers with one re-mint and plays (N26). A blob of non-decodable bytes then shows *stored, not decodable* after a single re-mint (E3).
- **P7 Bytes missing.** Delete the blob file: the missing-bytes message appears and no `src` is set.
- **P8 Disconnect.** Disconnect sends M2 (the session count drops). A Node replay of the old value, held only in process memory, gets 401 (N24).
- **P9 Unreachable.** Disconnect with the service stopped shows the disclosure text. After a restart, a replay gets 401 (N25).
- **P10 Same-site page.** A page on another port of the same host embeds `<video src>` pointing at M4. Run it at loopback (Fetch Metadata expected, so 403) and via a non-loopback name mapped to `127.0.0.1` (LAN-HTTP-like, [unverified]). Record the console CORP result, the bytes sent and zero effects (N08).
- **P11 MP4.** Record the MP4 `canPlayType` probe; play and seek the MP4 if the result is `probably` (G9).
- **P12 Local object URL.** With a local object URL present, no M4 request is made (N27).

**Screenshots.** Only of the player stage and of message states, never of Settings. **No token in a screenshot, log or report**: the run ends by grepping every output for the in-memory bearer and cookie values, as `docs/dev/lt-192.3-shared-mutations-result.md:259` did.
